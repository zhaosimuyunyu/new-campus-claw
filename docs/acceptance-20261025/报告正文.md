项目简介

CampusClaw 将课程、资料、作业管理与 AI 助手整合在一个平台内。用户可选择不同 AI 应用、编辑提示词模板、检索课程知识库、绑定或上传 Skill，并调用平台工具及外部 MCP 服务。每次运行记录模型请求、流式返回和工具结果，可在能力中心的运行追踪中查看及导出。

技术组成：Vue 3 + TypeScript + Vite 前端；Django / Django REST Framework 后端；PostgreSQL + pgvector 知识库；OpenAI 兼容模型接口；MCP HTTP 服务；临时容器中的 Python、Node、Shell 与 Chromium 执行环境。

03  /  问题一：每轮参数、返回与模板

结论：提示词模板会传入 LLM。每次用户提问可触发一次或多次模型请求；工具调用后还会继续请求模型，因此“一次对话”和“一次接口请求”不能混为一谈。

实际接口：POST https://ai-gateway.devops.hello1023.com/v1/chat/completions

请求字段 | Run 40 第一轮实际值 / 含义

model | course-chat

stream | true；以 SSE 接收流式返回

messages | 2 条：system（平台约束、应用角色、展开模板、绑定技能摘要）与 user（本次问题）；续聊可包含历史。

tools | 10 项候选工具声明；即使本轮不调用，绑定后的声明仍可能随请求发送。

其他参数 | 本次请求体未显式设置 temperature、top_p、max_tokens、tool_choice，不能把供应商默认值当成实际传值。

模板与用户消息原文

配置模板：你是 {{course}} 的实验助教。请用中文回答，先给结论，再列证据。
system 中实际文本：你是 第六课 · AI 能力实验室 的实验助教。请用中文回答，先给结论，再列证据。
user：请用两句话解释 Skill 和 MCP 的关系。

Run 40 聚合正文原文

Skill是课程中绑定的特定能力任务模块，例如本次的data-analysis技能负责数据分析相关任务；MCP是支撑这些技能实现的基础工具集合，提供代码执行、公式提示等具体功能，辅助技能完成对应任务。

这段返回证明接口确有回应，但把 MCP 说成“基础工具集合”不够准确。MCP 本质是模型应用与工具/资源服务之间的通信协议；本平台通过该协议接入具体工具。报告不把模型回答本身视为权威定义。

返回记录还包括 frames（原始 SSE JSON 帧）及 tool_calls。Run 40 最终 usage：prompt_tokens=1764、completion_tokens=557、total_tokens=2321；增量帧在 choices[].delta，结束原因取自实际 finish_reason。工具响应可出现正文为空但 tool_calls 非空的情形。认证头与密钥不进入追踪附件。

04  /  问题二：是否发送整个知识库

结论：不会固定发送全部知识库。实现先在当前课程内检索，关键词与向量结果通过 RRF 融合排序，最多取 4 个相关片段。仅将选中片段的标题、位置与正文写入 system。索引阶段的 embedding 调用与回答阶段的 LLM 调用是不同步骤。

对照设计：新建独立课程，上传并索引 6 份短文本，每份各有唯一标记 RAG-CONTROL-1 至 RAG-CONTROL-6；开启资料检索，询问验收规则和命中标记。该设计避免“知识库只有一小份资料，返回全文也看起来像检索”的歧义。

Run 47 观测项 | 实际结果

资料总数 | 6 份

retrieval.top_k | 4

returned_chunks | 4 个，按实际返回顺序为材料 1、6、3、2

实际请求包含的标记 | RAG-CONTROL-1, RAG-CONTROL-2, RAG-CONTROL-3, RAG-CONTROL-6

实际请求未包含的标记 | RAG-CONTROL-4, RAG-CONTROL-5

请求中命中片段一致性 | 逐项核对 returned_chunks.excerpt 与 system；命中正文进入请求，未命中标记缺席。

命中片段实例

阶段验收实验材料 1。唯一标记 RAG-CONTROL-1。本条规则是：项目验收需要演示第 1 个功能的具体请求和返回，并保留证据。

判断依据不是仅看 whole_knowledge_base_sent=false，而是对实际 llm_request.payload 做标记对照。原始 JSON 中可查到材料 ID、切片 ID、位置及检索得分。

边界说明

若知识库内容很少且全部被命中，发送片段可能恰好覆盖全库；“最多 4 个相关片段”并不保证每次一定少于全库。多轮会话还会携带历史文本，之前回答中的资料信息可能再次进入上下文。若无命中，当前实现直接回复未找到资料，不调用 LLM。关闭检索后，显式绑定的检索技能仍可能允许模型按需调用搜索工具。

05  /  问题三：绑定 Skill 会发送全文吗

结论：初始请求只发送已绑定技能的摘要与技能工具声明，不自动发送整个技能包。模型调用 read_skill 后，所选技能的完整指令会以 tool 消息进入后续请求；read_skill_resource 再按路径读取具体参考文件或脚本。

Run 41 轮次 | 本轮内容 / 返回 | 下一轮新增上下文

1 | system 含 data-analysis 名称和描述；模型请求 read_skill | 完整 instructions、资源文件名及运行说明

2 | 模型请求 read_skill_resource，路径 scripts/summarize_numbers.py | 该脚本的实际源码

3 | 模型请求 run_skill_script，传入 12、18、24、30 | stdout、stderr、exit_code、duration_ms 等结果

4 | 模型依据工具结果生成最终回答 | 平均数 21、中位数 21

初始请求中的实际摘要

data-analysis: 数据分析 — 从数据质量、统计方法到结论边界。

验证：以 read_skill 返回的完整 instructions 为对照，确认第一轮请求不含全文；第二轮最后一条 tool 消息包含该全文。源码包含 statistics.mean，直到读取脚本后才进入后续请求。上述比较在生成本报告时再次作了断言检查。

不能将“按需加载”误写成“全文永远不进入模型”。在同一次运行的工具循环内，已经加载的指令和源码会保留在后续 messages 中，因此后续请求可能包含完整 SKILL.md 和已读取的资源。未读取的整个资源目录不会自动拼接进 LLM 请求。

执行服务与模型的输入不同

run_skill_script 会把技能所需文件交给隔离执行服务，以支持脚本相对路径依赖；这不等于把所有文件内容发给 LLM。二进制资源由执行器使用，读取接口返回资源说明，不直接把二进制字节塞进模型文本。

06  /  问题四：Skill 的执行逻辑

实际流程：绑定技能 → 在 system 中声明摘要 → 模型产生工具调用 → 宿主检查技能是否已绑定 → read_skill 加载指令 → 按需读取资源 → run_skill_script 调用执行服务 → 结果写入 tool 消息 → 再次请求模型 → 输出答案与附件。Skill 本身是指令和资源包，不是自动执行任意代码的入口。

上传技能闭环（Run 46）

通过 /api/agent/skills/upload/ 上传 sample-skill.zip，HTTP 201，技能 ID 为 upload-2。技能包含 SKILL.md 与 scripts/summarize.py。绑定后，真实执行 read_skill → read_skill_resource → run_skill_script，三项工具均为 ok，并生成 outputs/summary.json，作为可下载产物保存。

生成内容：count=4、mean=21.0、median=21.0。上传是经正式应用接口完成，执行经过同一技能运行链，并非直接在报告脚本中计算来替代平台验证。

执行约束

脚本路径需位于已绑定技能的 scripts/ 目录，参数按 JSON Schema 验证。普通脚本在临时容器内运行，非 root、根文件系统只读、默认无网络，并限制 CPU、内存、进程数和运行时间（35 秒）。输出中的文件由宿主保存为受账号与课程权限保护的产物。仅指令型技能可能不执行脚本，而是指导模型按方法完成任务。

上游技能依赖特定插件、Git 工作区或外部账户时仍需对应环境；“内置了技能”不代表其所有外部能力均可无条件使用。

07  /  问题五：接入 MCP 后的请求

结论：LLM 仍接收 model、stream、messages，并额外接收当前绑定候选工具的 tools 声明。MCP 握手、服务 URL、会话和认证由宿主管理；模型不直接向 MCP 服务发送 HTTP 请求。

实际工具声明：Run 42 第一轮

{
  "type": "function",
  "function": {
    "name": "mcp_1_formula_hint",
    "parameters": {
      "type": "object",
      "title": "formula_hintArguments",
      "required": [
        "topic"
      ],
      "properties": {
        "topic": {
          "type": "string",

  }

模型返回调用 → 宿主调用 MCP

{
  "LLM tool_call": {
    "name": "mcp_1_formula_hint",
    "arguments": "{\"topic\":\"复合函数求导\"}"
  },
  "MCP method": "tools/call",
  "MCP params": {
    "name": "formula_hint",
    "arguments": {
      "topic": "复合函数求导"
    }
  }
}

宿主连接时执行 initialize → notifications/initialized → tools/list，将 name、description、inputSchema 转换为 LLM function 定义。模型返回 tool_calls 后，宿主验证工具候选集、参数及权限，再通过 JSON-RPC 2.0 调用 MCP。结果作为 role=tool 且关联 tool_call_id 的消息进入第二轮；随后模型给出链式法则说明。

本轮发现 6 项工具：formula_hint、unit_convert、learning_checklist、python_execute、shell_execute、browser_open；实验配置只绑定其中 4 项，因此请求中未声明另外 2 项。平台自己的 list_course_materials、create_pdf、create_docx 和技能工具也可能同时存在。

协议边界：目前实现 HTTP MCP（JSON / SSE），不支持 stdio。代码限制最多 6 轮模型请求、12 次工具调用；最后一轮移除工具并要求依据已有结果回答。
